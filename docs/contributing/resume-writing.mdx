This is step three of tailoring, after [job analysis and evidence selection](/contributing/resume-selection). It consumes the reviewed `ResumeSelectionPlan` and never decides on its own which experience to include.

## Pipeline

`packages/api/src/features/master-profile/writing/`:

1. **Skills** (`skills.ts`, deterministic). Candidates come from the plan. Order: skills the user chose, then included skills an included achievement shows (as a skill tag or in its text), then other included skills, then — only until the minimum is reached — relevant and other evidenced skills. Overlapping names (shared name or alias, or one name contained in another, e.g. "WordPress" and "WordPress Development") keep the first. Generic soft skills ("Communication", "Leadership") are left to the accomplishments unless the user included one on purpose. The list stops at the maximum. Each left-out skill keeps its reason.
2. **Wording** (`write.ts`). With _Adjust to the posting_, one AI call returns a headline, summary, a wording for each planned achievement and 2–4 skill groups. The prompt carries the ranked requirements, the plan's positioning, the region's spelling and the rules below. With _Use my exact wording_ no AI call is made.
3. **Acceptance** (`write.ts`, `grounding.ts`). Every planned achievement gets a wording. A rewrite is used only if it adds no number (existing grounding check), keeps the record's qualifiers ("about", "nearly", "~", "up to"…), names no tool or skill the record doesn't, and stays within the length budget; otherwise the user's text is used and a warning says why. The summary is trimmed to the sentence limit (trimming only removes text) and must pass the same checks. A headline must be built only from words in the included titles, organizations, scope, achievements and listed skills; otherwise the latest included position's title is used. Skill groups must place every chosen skill exactly once in 2–4 specific groups (no "Skills" or "Other"); otherwise the profile's own categories are used.
4. **Build** (`assemble/build.ts`). The plan's entries, its bullets in its order, the headline in `basics.headline`, skills in the accepted groups without proficiency levels, and the plan's section order applied within each layout column. Each resume item records which profile entry it came from.
5. **Quality checks** (`checks.ts`, deterministic). Run on the built resume before it's shown; they change nothing. Findings are stored with the assembly (`profile_assembly.result.writing`) and listed in the dialog, most serious first.

## Writing rules

`DEFAULT_WRITING_RULES` in `@reactive-resume/schema/resume-writing`. Guidelines, not limits: the writer aims for them and the checks warn; nothing the user chose is cut, and length is never fixed by shrinking text.

| Rule      | Default                                                                        |
| --------- | ------------------------------------------------------------------------------ |
| Region    | Canada: Canadian spelling, no photo, date of birth, age, marital status or SIN |
| Pages     | 2 with 5+ years of experience, otherwise 1 (estimated at ~500 words a page)    |
| Positions | usually 3–5                                                                    |
| Bullets   | 3–5 for major recent roles, up to 3 for others, at most 35 words each          |
| Summary   | 2–3 sentences, at most 75 words                                                |
| Headline  | on                                                                             |
| Skills    | 8–15, in 2–4 groups                                                            |

Other regions (US, UK, Australia, other) change spelling, personal-detail guidance and page targets.

## Resume Style Guide

`@reactive-resume/schema/resume-style`, stored per user in `resume_style_guide` (migration `20261103180159_resume_style_guide`), API `resumeStyle.{get, save, addExampleFromResume, addExampleFromFile}`, UI **Settings → Resume style**.

- **Presets** (up to 12) hold the writing rules above plus tone, bullet style, density (scales the words-per-bullet limit), recency (`recentYears`, `olderRoles: brief|full`), a fixed section order or the selection's recommendation, preferred skill-group names, notes and up to three examples. Templates exist for General, Communications, Digital Marketing, Project Management, Web Development and Other.
- **Choosing**: the preset the user picks in the build step, else the one whose keywords match the posting title most (word-start match), else the default (`choosePreset`).
- **Examples** (up to 6) are stored as text when added (from a resume via its Markdown, or from a PDF/DOCX/text upload). Saves can rename, annotate or remove examples but never change their text. The writer receives up to two excerpts (2,500 characters) as `STYLE_EXAMPLES`, for style only; a rewrite sharing six or more consecutive words with an example that aren't in the record is rejected.
- The report stores which preset was used (`writing.style`).

## Task models

`@reactive-resume/schema/ai-tasks`, stored per user in `ai_task_settings` (migration `20261103183158_ai_task_settings`), API `aiTasks.{get, save, check}`, UI **Settings → AI & developer → Models for each task**.

- **Tasks**: `extraction` (posting fields and job analysis), `evidence` (selection review), `writing` (resume wording), `polish` (career answers and replies when no schedule chose a connection), `review` (the resume reviewer). Each holds `providerId` (null: default connection), `model` (null: the connection's model) and `reasoningEffort` (sent as provider options only to OpenAI-like providers; see `reasoningOptions`).
- **Quality**: `standard` (default) or `thorough`. Thorough swaps the `thorough` setting in for `THOROUGH_TASKS` (evidence, writing, review) only when it has a model or connection (`taskSetting`). Requests pass `quality`; the assemble service otherwise uses the saved default. Nothing routes to the Thorough model without the user choosing it.
- **Resolution**: `ai-tasks/resolve.ts` builds the model; an unknown model name (`isUnavailableModel`: 404, or a 400/403 naming the model) retries once with the connection's own model and records `fallback` with a note. `selection/model.ts` (`askDefaultModel`) and `applications/ai.ts` (`generateJson` `fallback` option) both apply it.
- **Check**: `ai-tasks/check.ts` runs a small JSON request (with the reasoning option; on failure it retries without it, and a success then reports `rejected` and fails the check) and a forced tool call; the result is saved as `lastTest` and cleared when the setting changes.
- **Usage**: every model call records `{step, task, model, inputTokens, outputTokens, fallback}` on the selection plan (`plan.usage`) and the writing report (`writing.usage`, with `quality`). `TASK_TOKEN_ESTIMATES` gives the rough per-resume figures shown in settings. Suggested OpenAI model names (`SUGGESTED_OPENAI_MODELS`) are filled only on request and are never hard-coded defaults.

## Quality checks

| Severity                        | Codes                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Error: not backed by the record | `missing-source` (a bullet with no source or outside the reviewed selection), `unsupported-bullet` (more bullets than records), `title-mismatch`, `date-mismatch`, `entry-not-in-profile` (including qualifications), `unsupported-skill`, `placeholder`                                                                                                                       |
| Warning: worth improving        | `order` (not reverse chronological), `duplicate-bullet`, `duplicate-skill`, `skills-count` (over the maximum), `bullet-length`, `summary-length` (with a trimmed suggestion), `too-long` (over the page target, suggesting older bullets to drop), `cliche`, `keyword-repetition` (a posting term six or more times), `missing-section`, `missing-contact`, `personal-details` |
| Note                            | fewer skills than the target, too many groups, soft skills, short bullets, positions outside 3–5, a photo, unconventional headings, a short resume, missing education or phone/location                                                                                                                                                                                        |

## Tests

`writing/writing.test.ts`: skill choice (evidence, overlaps, soft skills, user choices, the maximum), group validation and fallback, qualifier and tool checks, rejection of invented numbers, tools, headline words and summary facts, every planned achievement worded, communications / web development / project management resumes built from plans with no error findings, tampered resumes producing each error code, length warnings without cutting, and the fallback to the user's own wording when the AI's answer is unreadable. `selection/service.integration.test.ts` checks the report is stored with the assembly. `writing/review.test.ts`: reviewer rewrites applied, held back (new number, changed claim, limit), unknown refs dropped, the draft kept when the review fails, edits paired as corrections and passed to the writer as preferences. `assemble/rendering.test.ts`: real PDF and DOCX of an assembled resume read back in full, and lost text and failed renders reported. `benchmark/benchmark.test.ts`: every case scored. The selection integration test covers revert/apply, feedback from edits, the profile staying unchanged, and the next writer prompt. `ai-tasks/resolve.test.ts`: Thorough applies only to its tasks and only when set, reasoning options per provider, unknown-model detection, default and chosen connections, and the fallback retry with usage.

## Line hygiene

`writing/hygiene.ts` holds deterministic clean-ups that only remove or reformat, never add a claim. The writing step (`tidyWritten`), the reviewer (each rewrite) and the build (every printed line, including verbatim mode) apply them:

- **Evidence notes** (`stripEvidenceNotes`): clauses after `;` or a dash that report where a figure came from or that it's unverified ("internal reporting… claimed", "was reported", "at that time"), undercutting tails ("without completing…") and parenthetical notes are removed. A main clause that is itself unsure is flagged `doubtful`. The build returns them as `evidenceNotes`, and checks report `evidence-note` so the user fixes the record.
- **Approximations** (`shortenApproximations`): "approximately 25" / "roughly five" → "~25" / "~5". Other qualifiers stay. `hedging` warns if long forms remain twice or more.
- **Tense** (`alignTense`): bullets open in the past tense; a current role written entirely in the present is left alone. `tense-mixed` reports what's left.
- **Titles, places, links, dates**: `titleWithOrganization` doesn't repeat an organization the title (or its acronym) already names; `shortLocation` gives "City, ON"; roles don't print the candidate's own site again and education prints no link; `datesOf` shows both ends at one precision.
- **Headline** (`singleHeadline`): one identity, the part before the first `|`. `headline-list` warns otherwise.
- **Political work** (`isPolitical`, `isPoliticalField`): left out of the plan unless the posting is in politics or government, with a reason the user can override. `sensitive-content` warns if it's included anyway.
- **Skills**: tools the included bullets name are listed whatever the posting asked (`isTechnical`); one-skill groups are merged (`mergeThinGroups`).
- **Length**: one page is the target below 10 years of experience (`pages.experiencedYears`). `selection/fit.ts` fits the proposal to it: while the estimate (`estimateWords`) is over `pages × wordsPerPage`, the weakest proposed achievement is left out (never one the user chose or marked always-include; positions keep one bullet), then the weakest projects and volunteer roles. Each says "Left out to fit the N-page target" and the plan gets a warning, so the user can include it again. The style preset is the one the posting would be written with. Rendering reports `render-sparse-page` when the last page is less than about a third full.
- **Filler and repetition**: `dropFiller` removes tails such as ", with additional projects in development"; `dropOwnName` removes the entry's own organization or project name from its bullets; a bullet under a degree or credential that only restates it is dropped (`restatesHeading`); `approximate-exact` flags "~38".
- **Skills**: skills the included bullets show (tools first) are listed before skills only marked relevant; a skill that repeats its group's heading is left out; group names use "&" and the writer keeps them to about 24 characters.
- **Headline**: the writer presents the candidate as the profession the posting hires, from their own skills and titles; descriptors such as "Professional" and "Specialist" are allowed because they claim no title.
- **Preset choice**: keywords matched in the title count double; the posting's summary and field count too, so "Officer, Recruitment" can still pick a communications preset.

The AI instructions say the same: the analysis ignores boilerplate, the evidence review rates risky or note-only records 0, the writer leaves out notes and unverified figures, writes past tense and one headline, and the reviewer looks for all of the above first.

## AI review

`writing/review.ts`, task `review`, prompt version `PROMPT_VERSIONS.review`. Runs once after writing, in rephrase mode with a plan, unless the request sets `review: false`.

- The prompt shows each bullet (`B1`…) with its record text, plus the requirements, headline, summary and skill groups. The answer is `{ score, findings: [{ category, severity, message, ref, rewrite, changesClaim }] }`.
- Rewrites of bullets and the summary go through the writer's checks (`bulletProblem`, `summaryProblem`). Passing, wording-only rewrites are applied up to `MAX_REVIEW_REVISIONS` (5); a rewrite flagged `changesClaim`, failing a check, or over the limit is `needs-review`. Unknown refs are dropped. One round only; the draft wording is kept as `before`.
- `assemble/revisions.ts` (`masterProfile.revision`): `revert` (applied → reverted), `apply` (needs-review or reverted → applied), `dismiss`. It swaps the line's exact paragraph in the resume JSON and refuses when the user has edited it since. A failed review leaves the draft as it was with a warning.

## Rendering validation

`assemble/rendering.ts`, after the resume is saved. It renders the PDF (`@reactive-resume/pdf/server`) and DOCX (`@reactive-resume/docx`) as exports do, extracts the PDF text with the ATS checker's pipeline (`extractPdf`, `buildExtractedDocument`, `analyzePdfResume`) and the DOCX body with `fflate`, then checks that the name, headline and every bullet are found (`textCoverage`), positions read in order, no page is blank, and the page count meets the target. Findings: `render-blank-page`, `render-text-missing`, `render-reading-order`, `render-pages`, `render-ats` (ATS blockers), `docx-text-missing`, and `render-failed` (info) when a file couldn't be produced. The report is `writing.rendering`.

## Feedback

`feedback.ts`, table `resume_feedback` (migration `20261103185726_resume_feedback`), API `masterProfile.feedback.{submit, list, delete}`. `correctionsFrom` pairs each generated bullet missing from the current resume with the most similar new bullet (token overlap ≥ 0.35), and records summary and headline edits. `feedbackBlock` gives the writer up to six notes and six corrections as `USER_FEEDBACK`, framed as style only. Feedback never writes to the master profile, and the writer's record checks still reject anything a correction states that the record doesn't.

## Benchmark

`benchmark/`: `cases.ts` (communications, web development and project management postings for one fictional record, with gold relevant/off-target achievements and needed skills), `run.ts` (the full pipeline without a database: optional analysis, selection, writing, review, build, checks, optional rendering), `score.ts` (relevance, recall, off-target, coverage of mandatory requirements, accuracy, rejected rewrites, writing issues, review score, skill precision/recall, redundancy, pages over target, formatting, ATS score, tokens, cost, time) and a Markdown report per family.

`pnpm benchmark:resumes` runs deterministic stand-in models as a regression gate. To compare real models, write a config file (format in `benchmark/live.ts`; API keys come from the environment variables it names) and run `RESUME_BENCHMARK_CONFIG=/path/to/config.json pnpm benchmark:resumes`; results go to `packages/api/reports/resume-benchmark.{md,json}`. To compare prompt versions, bump `PROMPT_VERSIONS` with the prompt change and compare the JSON from each version.

## Limitations

- Length is checked twice: estimated from word count (`too-long`) and, when the PDF renders, from its page count (`render-pages`).
- Feedback corrections are matched by wording similarity; a heavily rewritten bullet may not be paired with its source.
- Headline words are checked against the record word by word, so a good headline using a synonym falls back to the latest title.
